# 发布版本号规则

> 这份文档定的是**规矩**：以后每提交一批改动，版本号自己涨、更新日志自己追加。
> 你不需要在脑子里维护 "上一版是几点几"，跑一条命令就行。

---

## 1. 版本号长什么样

```
v 1 . 2 . 3
  │   │   └── PATCH  修订：修 bug、调数值、改文案、补文档
  │   └────── MINOR  次版本：新增可玩内容（机型 / 武器 / 舰船 / 界面 / 关卡）
  └────────── MAJOR  主版本：整块玩法或架构层面的变化
```

一直用三段式，**不写 `v1.2` 这种省略形式**，也不加 `-beta` 之类的后缀 ——
这个项目是静态托管、双击就能玩，没有预发布通道，加了后缀只会让"玩家那份到底是什么"
变成一个新问题。

当前版本写在两处，都由工具生成，**不要手改**：

| 位置 | 内容 | 谁生成 |
|---|---|---|
| `CHANGELOG.md` 每节标题 | `## [v1.0.0] 2026-10-15 · 正式发布` | `tools/release.js` |
| `js/version.js` | `BUILD_STAMP.version` | `tools/release.js`（顺带重算时间戳） |

---

## 2. 什么样的改动涨哪一位

判定顺序是**从高往低看，命中一条就停**。

| 判定 | 涨位 | 例子（都真的发生过） |
|---|---|---|
| 有一条提交被标成破坏性变动 | **MAJOR** | 挂载系统重构：单武器槽 → 分组挂载点 |
| 有新增功能的提交 | **MINOR** | 新增 11 艘水面舰船、新增战役选择层、机型 3 → 6 |
| 只有修复 / 调整 / 文档 | **PATCH** | 修极点附近的镜头卡动、修正注释里过时的数值 |

### 怎么标破坏性变动

三种写法任选其一，`release.js` 都认：

- 提交信息里带感叹号：`feat!: 挂载点不再是一对一`
- 提交信息里带方括号标记：`[major] 重做操控逻辑`
- 提交信息里出现 `BREAKING`

### 怎么标"这是新增功能"

`release.js` 先看**前缀**，认不出来再看**关键词**：

| 前缀 | 涨位 |
|---|---|
| `feat:` `feat!:` `[major]` | MINOR / MAJOR |
| `fix:` `docs:` `chore:` `refactor:` `test:` `style:` | PATCH |
| （没有前缀） | 看关键词：含「新增 / 新加 / 新的 / 加一个 / 重做」→ MINOR，否则 PATCH |

**所以以后提交尽量带前缀。** 不带也能跑（关键词兜底），
但兜底一定会误判 —— 比如「修文档里新增的那一节」到底是 feat 还是 fix。

## 3. 一条命令

```bash
node tools/release.js
```

它按顺序做四件事：

1. 从 `CHANGELOG.md` 最上面那条读出版本号与 `<!-- commit: xxx -->` 锚点
2. `git log <锚点>..HEAD` 取出这批新提交，按第 2 节的规则算出下一个版本号
3. 把新版本**追加到 `CHANGELOG.md` 顶部**，正文由提交信息自动分类成
   「新增 / 调整 / 修复 / 文档」四组
4. 由 `CHANGELOG.md` 重新生成 `js/changelog.js`（游戏内「更新记录」页读它），
   并刷新 `js/version.js`

这几个文件是**生成物，不要手改**：

```
js/changelog.js    ← 由 CHANGELOG.md 生成，游戏读它
js/version.js      ← 由工具生成，主菜单左上角的版本戳读它
```

想先看看会发生什么，加 `--dry`：

```bash
node tools/release.js --dry     # 只打印将要写入的版本号与条目，不落盘
```

## 4. 自动生成之后，人还要干什么

工具只会把提交信息搬过去，**它写不出人话**。所以自动跑完之后请顺手做两件事：

1. **把标题从提交前缀改成一句人话。**
   工具写的是 `feat: 新增战役选择层`，你要改成
   `## [v0.4.0] 2026-10-15 · 世界观与命名重整`
2. **把同类的几条合并成一条。**
   一次改动往往拆成五六个提交（"加功能" → "修它" → "再修它" → "补文档"）。
   玩家不需要看你的返工过程，合并成一句"新增战役选择层"就够了

`tools/release.js` 生成的条目里会插一条
`<!-- TODO: 合并同类项，改成一句人话 -->` 提示你。看到它就说明还没润色。

> **为什么不做成全自动**：版本号可以算，但"这批改动对玩家意味着什么"
> 算不出来。全自动的结果是更新日志变成提交记录的复读机，
> 而玩家要读的是**变化**，不是**提交**。所以工具负责机械的部分（版本号、
> 锚点、格式、文件生成），人负责那一句话。

## 5. 历史版本是怎么划分的

100 条提交按"一批改动做完了"分组，得到九个版本。分组依据是提交里
**换了一件事**的那个点，不是提交数量：

| 版本 | 主题 | 收尾提交 |
|---|---|---|
| v0.1.0 | 立项 —— 能飞起来的第一版 | `917f6d7` |
| v0.2.0 | 机库与挂载 | `9a4aaaa` |
| v0.3.0 | 资料库与六机型 | `cdee305` |
| v0.4.0 | 世界观与命名重整 | `4b8331c` |
| v0.5.0 | 镜头、僚机与轰炸机 | `82f74dc` |
| v0.6.0 | 操控重做 | `8573ec6` |
| v0.7.0 | 武器与制导收束 | `bac5ec4` |
| v0.8.0 | 全面体检 | `cb65241` |
| v1.0.0 | 正式发布 | `09c3686` |

v0.x 表示"还没到能推荐给陌生人的程度"：玩法在改、命名在改、设定在改。
到 v1.0.0 时这三件事都停了，才挂上 1.0。

## 6. 两个例外

**只改文档，不发版本。** 如果这批提交全部落在 `docs/` 或 `*.md` 里，
`release.js` 只刷新两个生成物（`js/changelog.js` 与 `js/version.js` 的时间戳），
不涨版本号 —— 文档改动对玩家不可见，为它占一个版本号会让"版本"变成噪音。
想强制发版，加 `--force`。

**一个版本号只发一次。** 已经写进 `CHANGELOG.md` 的版本号不会再被复用。
如果不小心跑重了，删掉 `CHANGELOG.md` 顶部那一节，再跑一次即可 ——
`release.js` 永远只看最上面那条的锚点。
