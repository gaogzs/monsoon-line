# 发布版本号规则

> **版本号完全由人定。** 发版时把版本号写进命令，脚本负责追加更新日志草稿、
> 检查版本号只往上走、刷新游戏读的两个生成物。
>
> 以前 `release.js` 会按提交信息自动判大 / 中 / 小版本（`feat` → 中版本、
> `fix` → 小版本……），从 v1.10.0 之后取消了：一批改动对玩家算多大，
> 提交前缀判断不了。

---

## 1. 版本号长什么样

```
v 1 . 2 . 3
  │   │   └── PATCH  修订：修 bug、调数值、改文案、补文档
  │   └────── MINOR  次版本：新增可玩内容（机型 / 武器 / 舰船 / 界面 / 关卡）
  └────────── MAJOR  主版本：整块玩法或架构层面的变化
```

一直用三段式，**不写 `v1.2` 这种省略形式**，也不加 `-beta` 之类的后缀 ——
这个项目是静态托管、双击就能玩，没有预发布通道，加了后缀只会让"玩家那份到底是什么"
变成一个新问题。

当前版本写在两处，都由工具写入，**不要手改**：

| 位置 | 内容 | 谁写 |
|---|---|---|
| `CHANGELOG.md` 每节标题 | `## [v1.0.0] 2026-10-15 · 正式发布` | `tools/release.js`（版本号是你在命令里给的） |
| `js/core/version.js` | `BUILD_STAMP.version` | `tools/release.js`（顺带重算时间戳） |

---

## 2. 涨哪一位：自己定

上面三段的含义是参考，不是脚本规则 —— 一批改动对玩家算多大，由发版的人判断。
脚本只做两项检查：

- 格式必须是三段式 `vX.Y.Z`（`v` 可省略）；
- 必须**比当前版本大**（按数字比，`v1.10.0 > v1.9.0`）。用过的版本号不能再用。

游戏内「更新记录」页的「大版本 / 中版本 / 小版本」标签仍按版本号本身显示
（`X.0.0` 大、`X.Y.0` 中、其余小），只是标签，不参与任何判定。

---

## 3. 命令

```bash
node tools/release.js v1.11.0          # 发 v1.11.0
node tools/release.js v1.11.0 --dry    # 只打印将要写入什么，不落盘
node tools/release.js                  # 不发版，只重新生成两个生成物
```

带版本号时按顺序做四件事：

1. 从 `CHANGELOG.md` 最上面那条读出当前版本号与 `<!-- commit: xxx -->` 锚点，
   检查新版本号比它大
2. `git log <锚点>..HEAD` 取出这批新提交（一条都没有就报错退出）
3. 把新版本**追加到 `CHANGELOG.md` 顶部**，正文按提交前缀分成
   「新增 / 调整 / 修复 / 文档」四组草稿（分组只影响草稿排版，与版本号无关）
4. 由 `CHANGELOG.md` 重新生成 `js/core/changelog.js`（游戏内「更新记录」页读它），
   并刷新 `js/core/version.js`

不带版本号只做第 4 步。

这几个文件是**生成物，不要手改**：

```
js/core/changelog.js    ← 由 CHANGELOG.md 生成，游戏读它
js/core/version.js      ← 由工具生成，主菜单左上角的版本戳读它
```

---

## 4. 自动生成之后，人还要干什么

工具只会把提交信息搬过去，**它写不出人话**。所以自动跑完之后请顺手做两件事：

1. **把标题从提交前缀改成一句人话。**
   工具写的是 `feat: 新增战役选择层`，你要改成
   `## [v0.4.0] 2026-10-15 · 世界观与命名重整`
2. **把同类的几条合并成一条。**
   一次改动往往拆成五六个提交（"加功能" → "修它" → "再修它" → "补文档"）。
   玩家不需要看你的返工过程，合并成一句"新增战役选择层"就够了

`tools/release.js` 生成的条目里会插一条
`<!-- TODO: 合并同类项，改成一句人话 -->` 提示你。看到它就说明还没润色。

> **为什么不做成全自动**："这批改动对玩家意味着什么"算不出来 ——
> 版本号涨哪一位也是同一个问题，所以现在也交给人。全自动的结果是更新日志
> 变成提交记录的复读机，而玩家要读的是**变化**，不是**提交**。
> 工具负责机械的部分（锚点、格式、版本号检查、文件生成），人负责版本号和那一句话。

---

## 5. 历史版本是怎么划分的

100 条提交按"一批改动做完了"分组，得到九个版本。分组依据是提交里
**换了一件事**的那个点，不是提交数量：

| 版本 | 主题 | 收尾提交 |
|---|---|---|
| v0.1.0 | 立项 —— 能飞起来的第一版 | `917f6d7` |
| v0.2.0 | 机库与挂载 | `9a4aaaa` |
| v0.3.0 | 资料库与六机型 | `cdee305` |
| v0.4.0 | 世界观与命名重整 | `4b8331c` |
| v0.5.0 | 镜头、僚机与轰炸机 | `82f74dc` |
| v0.6.0 | 操控重做 | `8573ec6` |
| v0.7.0 | 武器与制导收束 | `bac5ec4` |
| v0.8.0 | 全面体检 | `cb65241` |
| v1.0.0 | 正式发布 | `09c3686` |

v0.x 表示"还没到能推荐给陌生人的程度"：玩法在改、命名在改、设定在改。
到 v1.0.0 时这三件事都停了，才挂上 1.0。

---

## 6. 两条约定

**只改文档，一般不发版本。** 文档改动对玩家不可见，为它占一个版本号会让
"版本"变成噪音。这条现在由人把握：不想发就别带版本号跑，只刷新生成物。

**一个版本号只发一次。** 脚本拒绝不比当前版本大的版本号。
如果不小心发错了，删掉 `CHANGELOG.md` 顶部那一节，再用正确的版本号跑一次 ——
`release.js` 永远只看最上面那条的版本号与锚点。
