# 总设计文档

《季风线》MONSOON LINE —— 零依赖浏览器空战游戏

> 本文档面向**修改这个项目的人**，记录的是"为什么这么做"，
> 而不是"做了什么"（后者读代码更快）。凡是看起来可以随手改、
> 其实有具体原因的地方，原因都写在这里。

---

## 1. 项目定位

| 项 | 决定 | 原因 |
|---|---|---|
| 运行形态 | 双击 `index.html` 直接玩 | 免安装、免构建、可离线、可邮件发送 |
| 依赖 | **零**。无框架、无库、无外部资源 | 十年后依然能跑；不用处理依赖腐烂 |
| 渲染 | Canvas 2D 手写三维管线 | 见 [rendering.md](systems/rendering.md#为什么不用-webgl) |
| 音频 | WebAudio 全程序化合成 | 没有音频文件要分发，也不会有加载失败 |
| 模块化 | 经典 `<script>` + 全局命名空间 | ES module 在 `file://` 下会被 CORS 拦死 |
| 规模目标 | 小体量、内容完整 | 宁可十关做完，不要二十关做一半 |

## 3. 模块划分与加载顺序（层 + 约定）

**加载顺序只有一个权威来源：`tools/build/gen-index.js` 的层规则**；各语言页面副本
（`locales/<语言>/html/index.html`）里的 `<script>` 块由 `tools/build/gen-pages.js` 按它生成，不手改。规则：

1. 按固定的**层**：`core → data → models → missions → engine → render → ui → boot`；
   每个命名空间的 `_state.js`（只建一个空壳 `var NS = { $: {} }`）排在 `core` 之后、其余层之前，
   所以同一个命名空间的文件可以按职责放进不同的层。
2. 层内：`_` 开头的文件（共享库、`_schema.js`）整层最先，`zz` 开头的（`zz-seal.js`、
   `zz-api.js`）整层最后，其余按目录与文件名字母序。
3. `core/` 里有一份人工指定的先后：version、changelog、math3d、**text**、registry、tags；
   语言包 `locales/zh-CN/text.gen.js`（以及页面自己的语言）紧跟 `text.js`
   （文本机制与文本必须先于一切要写 `T('键')` 的文件）。

加一个单位 = 新建一个文件 + `node tools/build/gen-pages.js`。`smoke.js` 断言页面副本
与目录、模板、文本一致，忘了跑会在测试里炸，而不是在玩家屏幕上白屏。
页面与启动器见 [systems/pages.md](systems/pages.md)。

**注册表**（`core/registry.js`）：数据文件只写 `Registry.aircraft({ id, order, … })` 之类的调用；
每层最后的 `zz-seal.js` 调一次 seal，生成消费者代码读的全局（`AIRCRAFT` `SHIPS` `PLATFORMS`
`WEAPONS` `TURRET_GUNS` `TARGETS` `MODELS` `MISSIONS` `CAMPAIGNS` `CODEX`），然后冻结该层。
重复 id 在注册时抛错。

**大命名空间怎么拆**：`Ent` / `AI` / `HUD` / `Game` / `PLANFORM` / `RenderEnv` 原来各是一个
巨型闭包。现在每个都有一个私有状态对象 `NS.$`，各文件写成
`(function (NS) { var $ = NS.$; … })(NS)`：

- 只在一个文件里用到的变量 / 函数保持局部；
- 被别的文件用到的函数写成 `$.fn`（定义处文件顶部补 `$.fn = fn;`）；
- 被别的文件用到的变量，所有引用（含声明）都改成 `$.x`；
- 公开接口集中在 `zz-api.js`：`NS.key = $.key`。
- **规则**：一个命名空间的 `$` 只许该命名空间自己的文件读写，跨命名空间只能走公开函数。
  `smoke.js` 有静态检查。公开接口表见 [systems/modules.md](systems/modules.md)。

**标签**（`core/tags.js`）：单位的独有机制 = 数据里一个标签 + 机制代码认标签，
机制代码里不出现具体单位 id。见 [systems/tags.md](systems/tags.md)。

**文本**（`locales/`）：玩家可见的文字只在 JSON 里，脚本里只写 `T('键')`。
见 [systems/text.md](systems/text.md)。

> 旧的单文件布局（`data.js` `models.js` `missions.js` `entities.js` `ai.js` `hud.js` `game.js`
> `codex.js` `planform.js` `render-env.js`）已经拆完；对照关系见
> [systems/modules.md](systems/modules.md#旧文件--新位置)。重构前的原版整份留在 `backup/`。

**注意**：`js/boot/zz-api-game.js` 末尾的 `window.addEventListener('load', ...)` 启动游戏。
它必须最后加载（`zz` 前缀保证了这一点）。

## 4. 运行时架构

### 4.1 状态机

`Game` 内部用字符串 `state` 表示当前屏幕，取值与 DOM 屏幕 id 一一对应：

```
title · campaign · brief · hangar · codex · settings · help · changelog · playing · debrief
```

- `show(id)` 是唯一的屏幕切换入口：清掉所有 `.screen` 的 `active`，
  给 `#scr-<id>` 加上
- **`data-go` 按钮由 `show()` 统一驱动**。这里没有兜底 `else`——
  早先的写法让任何拼错的 `data-go` 值都静默跳回标题页，出问题时
  完全看不出哪里错了。现在未知值什么也不做
- `playing` 不是 DOM 屏幕，所有 overlay 都会被隐藏
- **`failing` 是 `playing` 的子状态**（不是新的 `state` 值）：`Game.failing = { t0, hold, fail }` 非空时，世界继续模拟、输入冻结、HUD 压暗，弹出失败提示；`FAIL_HOLD_S`（起步 5 s，不短于失败台词时长）之后或点"结束"才 `finish(false)` 进 `debrief`
- **`campaign` 是标题与简报之间的一层。** 它决定"打的是哪一场仗"，
  而"选哪一关"留在简报页（那里才有目标、威胁与情报）。
  战役清单由 `CAMPAIGNS`（`js/missions/`）驱动，
  加新战役不需要动 `index.html`
- **`changelog` 的内容一个字都不在界面代码里。** 它读全局 `CHANGELOG`
  （`js/core/changelog.js`，由 `tools/build/release.js` 从根目录 `CHANGELOG.md` 生成），
  所以发新版本不需要动界面。见 [6.9](#69-为什么更新日志要生成两次)

**关卡索引只有一套**：`missionIdx` 始终是 `MISSIONS` 的全局下标，
`activeCampaign` 只决定"简报页列出哪几关"和"返回回到哪一层"。
不要为战役另建一套局部索引 —— 两套索引之间来回换算，
是这类分层界面最容易长出的一类 bug。

### 4.2 主循环

```
requestAnimationFrame(loop)
  └─ dt 上限 0.05s（切标签页回来时不会瞬移）
     └─ update(dt)  → 输入 → 实体 → 碰撞 → 任务逻辑 → 胜负 → 相机
     └─ render()    → Renderer.begin → pushModel×N → flush → 粒子 → HUD
```

暂停时 `update` 不跑但 `render` 照跑——**这是设置能热调整的前提**：
玩家在暂停菜单里拖动 FOV 滑块，画面立刻变。

### 4.3 世界对象

`world` 是每关新建的普通对象，没有类：

```js
{
  time, actors[], missiles[], bullets[], particles[], targets[],
  wings{}, player, flags{},
  objective, objectiveSub,
  detected,
  killed, hitsLanded, shotsFired,
  groundKilled,                       // 被摧毁的地面/海面目标，单独计分
  timeLimit, timeLeft,                // 关卡时限（秒），0 = 不限时
  fireMissile(actor, target), radio   // radio 指向 Radio 模块
}
```

`flags` 是一个自由字典，任务脚本用它做一次性触发
（如 `flags.tallyDone`）。**加新触发器时记得用独一无二的键名**，
它不分区、不清理。

## 5. 关键约定

改代码前必须知道这几条，否则会踩坑。

### 5.1 坐标系

**x = 右，y = 上，z = 前**，右手系，满足 `right × up = fwd`。
世界 +z 的**真方位**按关卡而定：`mission.axis`（度），默认 0 = 北。罗盘、方位报读与简报地图都加上它；物理与 AI 只看世界坐标。
单位是**米**。模型一律**机头朝 +z、右翼朝 +x、座舱朝 +y**。

### 5.2 姿态用正交基，不用欧拉角

飞机姿态是三个互相正交的向量 `fwd / up / right`，每帧对它们做局部旋转
（罗德里格斯），最后 `M3.orthonormalize()` 修正漂移。

**不要改成欧拉角。** 垂直姿态时欧拉角有万向节锁，而这个游戏有大量
垂直机动（高空缠斗、筋斗）。

### 5.3 相机不跟随滚转（追尾视角）

追尾视角的 `up` 恒在世界 +Y 附近，所以地平线永远是水平的，天空可以用
简单线性渐变填充。**座舱视角才跟随滚转**。

如果改成跟随滚转，`drawSky` / `drawGround` 全部要重写（地平线会倾斜）。

### 5.4 面不做背面剔除

`render.js` 把所有面按深度排序后全部绘制，不做背面剔除，光照取
`|dot(normal, light)|`。

原因：低多边形模型可能有洞、绕序不一定一致，剔除会导致随机缺面。
代价是绘制量翻倍，但当前规模扛得住。

### 5.5 尺度是压缩过的

飞机长约 20 m，相机在机后 74 m（可调）。速度、射程都经过压缩，
让交战发生在视觉上"热闹"的距离。**不要**把这些数字改成真实值——
真实比例下 9 km 外的敌机只有几个像素。

### 5.6 屏幕用 DOM，不用 Canvas 画 UI

所有菜单、机库、简报、设置都是 HTML。只有 HUD 画在 Canvas 上。

原因：DOM 让文本排版、滚动、表单控件全部免费。

## 6. 关键设计决策回顾

这一节记录几个**当时踩过坑才定下来**的决定。

### 6.1 为什么有"开机自检"

`preflight()` 在 `Game.init()` 第一行运行，检查所有模块是否加载、
所有数据引用（机型→模型、机型→武器）是否成立。有问题就在屏幕底部
弹出红条。

这是**开发环境没有 shell** 时的补偿手段：当时无法运行 node 做语法检查，
只能让游戏自己报告。现在 `tools/test/smoke.js` 已经覆盖了这件事，
但自检对最终用户仍然有价值（比如文件没下载全）。

### 6.2 为什么操作说明是 JS 生成的

操作说明同时出现在两个地方：独立的"飞行手册"页，和暂停菜单里的
"操作说明"页签。

早期这两处是**两份独立的 HTML**，改一个忘一个。现在统一由
`buildHelpHTML(forPause)` 生成，按键表 `KEYMAP` 和要诀 `TIPS`
是唯一数据源。

### 6.3 为什么设置项是数据驱动的

`SET_GROUPS` 描述了所有设置项（类型、范围、单位、标签），
`buildSettingsInto(container)` 把任意容器填满控件。

所以独立设置页和暂停菜单里的设置页**共用全部代码**，加一个新设置项
只需要往 `SET_GROUPS` 里加一行。

### 6.4 为什么暂停菜单是页签式的

暂停时需要调设置，且要**实时看到画面变化**。如果设置是独立页面，
玩家就得退出去再进来。所以设置直接嵌在暂停覆盖层里。

### 6.5 为什么挂载是"点"而不是"槽"

早期是每架飞机一个特殊武器槽，从三选一里挑。

改成**成对的挂载点组**之后，玩家的决定从"挑哪一个"变成
"每个位置各装什么"：

- 适配限制制造取舍（翼尖挂不了反舰弹）
- 同种武器占多组会累加弹药与齐射数，于是"集中带一种"与
  "分摊带几种"成了真实的选择
- 空置能换回机动性，所以"带多少"本身也是一个决定

代价是 UI 复杂度上去了一大截（机库要一张挂载表，HUD 要一个纵列表）。
这笔交易划算，因为机库是这个游戏唯一让玩家做长期规划的地方。

见 [loadout.md](systems/loadout.md)。

### 6.6 流程顺序：先简报后机库

早期流程是"选机体 → 看简报"，但简报里写着这一关的威胁（防空网？
高空拦截？），而机体选择本来就该依据威胁。所以改成
**简报 → 机库 → 出击**。

### 6.7 为什么标题与简报之间多了一层战役选择

原本"开始任务"直接进简报，而简报页顶部的关卡选择器已经把全部关卡都列出来了。
只有一场战役时，这一层确实是多余的。加它的理由不是现在，是以后：

- **关卡与战役是两种不同的决定。** "打哪一场仗"属于战略层，
  "这一场里选哪一关、带什么机体"属于任务层。战役越多，
  把所有关卡平铺在一个清单里就越读不懂。
- **选关留在简报页，不另建一个选关屏。** 简报页才是"这一关是什么"的
  唯一权威（目标、威胁、情报、地图全在那儿）。另做一个选关屏就要把
  这些信息复制一份，而两份一定会脱节。
- **加战役不需要改界面代码。** 清单由 `CAMPAIGNS` 数组生成，
  战役名、起止时间、简述都写在数据里；`Game` 只是把它画出来。

代价是多了一次点击。这笔交易划算，因为"以后还会有别的战役"
是已经确定的事，而那一刻再补这一层就要动所有返回按钮。

### 6.8 为什么通关记录按任务 id 记，不按下标

`cleared` 原来按 `missionIdx`（`MISSIONS` 的全局下标）记。加入新战役后
关卡会继续往后追加，**旧下标的含义可能漂移**；按下标记进度，
迟早会出现"打了 A 关，B 关亮了"。

改成按 `MISSIONS[i].id` 记之后，索引怎么变都不影响已有记录，
战役进度也只是"把它名下几关的 id 数一遍"。

### 6.9 为什么更新日志要生成两次

玩家能看到的更新日志有两种形态，各自有各自的用处：

- **`CHANGELOG.md`（根目录）** —— 给人读的。写它的地方是 pull request、
  是 review、是"这一版到底改了什么"的讨论。格式是 Markdown，带 `###` 分类。
- **`js/core/changelog.js`** —— 给游戏读的。浏览器里没有 Markdown 解析器，
  而为了这一屏去装一个（哪怕是最小的）都违反"零依赖"这条底线。

所以中间放一个 `tools/build/release.js`：它**读 Markdown、写 JS 对象**。
两边都是纯数据，没有一行渲染逻辑 —— 界面只负责把 `CHANGELOG.releases` 画出来。

顺手它还解决了两件本来会反复出错的麻烦事：

- **版本号只有一个来源。** `CHANGELOG.md` 顶部那条是版本号的定义处；
  `js/core/version.js` 与 `CHANGELOG.current` 都从它派生。三处手写必然对不上。
- **"这一版之后有哪些提交"不需要人记。** 每个版本条目里带一个
  `<!-- commit: xxx -->` 锚点，`release.js` 用 `git log <锚点>..HEAD`
  取新提交写成草稿。锚点就是"上一版发到哪儿"的记号。
  版本号本身由人在命令里给（`node tools/build/release.js vX.Y.Z`），脚本只检查它比当前版本大。

代价是**多了一份生成物要同步**，而生成物一定会有人忘了重新生成。
所以 `tools/test/smoke.js` 里加了一条硬断言：把 `CHANGELOG.md` 现场解析一遍，
和要求 `js/core/changelog.js` 逐字段相等 —— 忘了跑 `release.js` 会在测试里炸，
而不是在玩家屏幕上显示一份过期的日志。

规则写在 [VERSIONING.md](VERSIONING.md)。

## 7. 性能策略

| 手段 | 位置 | 说明 |
|---|---|---|
| 对象池 | `render.js` `getP()` / `getFace()` | 避免每帧分配上千个临时对象 |
| 颜色量化缓存 | `render.js` `shade()` | 亮度/雾浓度各 16 档做 key，缓存 rgb 字符串 |
| 屏幕面积剔除 | `render.js` `pushModel` | 投影后小于 1.6 px² 的面直接丢弃 |
| 距离剔除 | `render.js` `drawClouds` | 超过 16 km 的云不画 |
| 帧率上限保护 | `Game` `loop` | `dt` 钳到 0.05s |

**当前瓶颈**是 Canvas 的 `fill()` 调用次数。如果帧率不够，
优先降低 `MODELS` 的面数，而不是优化 JS 数学。

## 8. 已知问题与待改进

诚实清单，按优先级排列。

### 需要处理

1. **没有可访问性支持**：纯鼠标键盘操作，无手柄、无 `prefers-reduced-motion`
2. **菜单不能用键盘导航**：`Tab` 键在游戏内被占用（切目标），
   菜单里应该单独支持
3. **结算后 `world` 未释放**：`finish()` 后 `player`/`world` 仍持有引用，
   连续玩多关会累积内存
4. ~~**只有一个存档点**：`cleared` 记录在内存里，刷新页面就丢~~ **已解决（2.6）**：`cleared` 与机库挂载 `loadouts` 存进 `localStorage['monsoonline.save.v1']`（`js/engine/game/save.js`，格式 `{ v: 1, cleared, loadouts }`），读写都静默降级；存下来的挂载读取时逐组校验，不合法的回退默认。仍然没有"多个存档位"和进行中的关卡存档

> 原第 3 条"任务目标缺少屏幕内指示"已解决：`HUD` 的 `drawOffscreen()`
> 把屏外目标钉在安全矩形边上，已锁定目标另有专属提示（v1.4.0）。

### 可以但没必要

5. 相机与 HUD 的缩放（`hudScale` 曾计划做，最后换成了 `hudOpacity`）
6. 更多机型与武器（数据结构已支持，缺的是数值设计和模型）
7. 手绘贴图/精灵替代纯色面

## 10. 如何加一关

1. 在 `js/missions/` 末尾 `MISSIONS.push({...})`，字段照抄现有任何一关
2. 必须提供：`id` `no` `name` `en` `loc` `date` `altStart` `speedStart`
   `prose` `objectives` `threats` `intel` `map` `spawn()` `tick()` `win()` `lose()`；
   可选 `timeLimit`（秒，倒计时由 `Game` 统一处理，归零判负）
3. 在 `js/data/` 的 `VOICES` 里加同名 `id` 的台词表，至少要有 `start`
4. **把它的全局下标写进某个战役的 `missions` 数组**（见下一节）——
   漏了这一步，关卡会存在但永远选不到，`preflight()` 会报出来
5. 跑 `node tools/test/smoke.js`——它会自动检查新任务的字段完整性；
   再跑 `node tools/test/probes/probe-missions.js`——确认清空敌人之后这一关真的能赢

`map` 里的坐标是**世界米**，相对进入点。绘图由 `drawMap()` 统一处理。

**给这一关的 NPC 配挂载时先读 [missions.md「给 NPC 设计挂载」](systems/missions.md#给-npc-设计挂载)**：
上游 NPC 用逐组 `loadout` 指定，每一条都必须符合该挂点的选项限制
（`fits` ∩ `canCarry`），写错会进 `Ent.mountIssues`，`smoke.js` 会拦；
下游 NPC 只写 `special`（+ 可选 `pods`），它们的 `npcFits` 已经保证适配。
注意带上对地弹的敌机会真的去炸海面/地面目标 —— 那是在改这一关的胜负条件。

## 11. 如何加一场战役

1. 在 `js/missions/` 的 `CAMPAIGNS` 里 `CAMPAIGNS.push({...})`，
   提供 `id` `no` `name` `en` `sub` `loc` `period` `desc` `missions`
2. `missions` 里写**全局下标**，且每个下标只能属于一个战役。
   新战役的关卡接着 `MISSIONS` 末尾追加，所以下标是连续的
3. **不要动 `index.html` 和 `Game`** —— 战役屏由 `CAMPAIGNS` 生成。
   将来才做的战役可以写成 `missions: []`，它会以"资料封存"的
   不可点卡片出现在列表里（那类卡片**不写地名与年份**，
   免得提前承诺还没定的设定）
4. 跑 `node tools/test/smoke.js`：它检查每一关都恰好归属一个战役，
   并断言"点进战役后简报页列出的关卡数 = 该战役的关卡数"

建议把战役的中文名与英文代号也写进 `js/ui/codex/` 的「战役 / CAMPAIGN」条目，
两份文案应当同源 —— 资料库那份是完整的战略叙述，列表卡片是它的压缩版。
